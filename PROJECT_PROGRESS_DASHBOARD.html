Completed features

  • OTP regeneration: resend path includes expiry, attempt limits and rate limiting; covered by backend tests.
  • Payments: GCash, Maya and MariBank selection, method-specific QR display and server-side availability checks are wired. Three local QR assets are present; their live payment destination and production URLs still need validation.
  • Proof of payment: uploaded file is linked to booking/payment and served through an authenticated endpoint with access checks and private cache headers.
  • Dashboard access: bounded API calls and independent request results allow usable error states instead of an endless initial spinner.
  • Booking filters: Pending, Verified, Completed and Canceled filters/counts are implemented in the customer history view.
  • Notifications: SMS/push delivery records, provider result handling, booking customer targeting and reminder deduplication have local tests. Tests do not prove handset/browser receipt.
  • Forecast data guard: imports preserve other tables and reporting distinguishes observed data from imputed dates; 30 actual dates are not currently available.
  • Core operations: POS, inventory, purchase orders, admin workflows, authentication/privacy endpoints and public content are present in source and domain tests.

Ongoing tasks

  • Validate and apply migrations against the intended deployed database; the test suite uses isolated SQLite and does not establish production schema state.
  • Set durable backend media storage and verify a proof upload survives service restart.
  • Configure verified SMS/email credentials and push VAPID keys; schedule delivery workers/reminders and test authorized real recipients/devices.
  • Provide a validated sales export with at least 30 observed sales dates; do not synthesize transactions to fill gaps.
  • Verify production QR image URLs and confirm the codes resolve to the studio’s intended accounts.
  • Run browser acceptance/accessibility checks, physical receipt printer checks, and a supported Android/Gradle build.
  • Resolve React test act(...) warnings in asynchronous booking-calendar tests.

Pending features

  • Dedicated reports/sales modules: backend/apps/reports and backend/apps/sales currently contain placeholder views/tests; existing reporting is implemented in other domains.
  • Gallery administration: public gallery viewing exists, but staff/admin CRUD workflows are not present.
  • End-to-end release evidence: no production-like browser journey, live notification receipt, or Android artifact is evidenced in this audit.

Identified issues and limits

Data
Forecast history is too sparse for the 30-day target

Bundled July 2025 CSV: 24 transaction rows across 11 distinct recorded dates. Forecast code can report missing coverage, but real history must come from a validated business export.

Integrations
Mock/provider acceptance is not live delivery

SMS, push, email and chatbot tests exercise local logic or mocked adapters. Production credentials, scheduling, network delivery and recipient confirmation are not established.

Database
Production migration state was not checked

Migration drift is clean and tests create an isolated database. No claim is made that the live database has applied the current migration graph.

QA
Two backend tests are skipped on SQLite

They require PostgreSQL row-lock behavior. Run those cases against the target PostgreSQL engine before relying on concurrency guarantees.

Frontend QA
React async test warnings remain

All frontend assertions pass, but calendar availability updates produce act(...) warnings in the customer dashboard tests.

Scope
Production security and secret/dependency gates not refreshed

This audit did not run live deployment checks, npm/pip vulnerability scans, or the repository secret scanner. CI configuration exists; current gate status is unverified here.

Recommended next steps

  1. Close data and schema gaps: load a real sales export, validate forecast dates, and run migrations plus smoke tests on a staging copy of the production database.
  2. Prove payment and file persistence: set production-accessible QR URLs, validate account ownership, configure persistent media storage, and test an authorized booking proof upload/retrieval.
  3. Activate notifications: configure SMS/email/push credentials and schedules, then verify delivery to an authorized handset/browser and inspect delivery logs.
  4. Clear release gates: run the secret and dependency scans, deployment security checks, browser/accessibility acceptance, and PostgreSQL concurrency tests.
  5. Finish scoped features: decide whether gallery administration and dedicated reports/sales modules are required for launch; implement and test them if in scope.
  6. Build native target: validate a supported JDK/Gradle pairing and produce an Android artifact.
